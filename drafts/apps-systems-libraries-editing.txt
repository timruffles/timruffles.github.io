title: "Applications, systems, libraries: which are you writing?"
draft: true
date: "2023/02/17"
body: |

  A lot of coding 'rules' miss an important piece of context: are they rules for application, library or system programming? They're different beasts, and applying rules or habits from one to another is silly. I have a hunch many disagreements arise because the disputants do different types of programming.

  Applications do specific things for users: a stock trading app, a game, etc. The hart part of application programming is maintaining speed of delivery with ever-growing complexity.

  Libraries are reusable utilities bits of code, not full applications themselves. They need to be complete, correct, and fast enough to compete with other libraries.

  Systems solve problems a layer below the reason a user is engaging with software: the HTTP server your app uses, its databases, the operating system. The hard part is that the implementation must be totally correct and generally extremely fast. But the work is often well specified (often formally, e.g. RFCs), and changes slowly. Taken together, this means investment in quality has a huge payoff.

  The problem I've seen most is applying rules or values from library and system programming when building applications.


  It's important to distinguish true libraries that should fit into any application, from application libraries (really just shared bits of application code).
   True libraries should make as few assumptions as possible to make them easy to adopt. They shouldn't make decisions on things like logging where applications may differ. Libraries should be complete without surprising edge-cases, and often need to be pretty fast to be competitive. Application libraries can, and probably should, accept far more coupling to the application's assumptions (e.g. they can have dependencies on other application and third-party libraries). They can also solve just the subset of the problem the application needs. i.e. it's fine to not consider HTTP PATCH in some app library that never use it.

  ## Does the rule make sense for what you're doing?

  As an example, in Go we hear that types should have a useful zero value, i.e. an uninitialized value of a type shoudl be useful and safe. This works really well for some some built-in or standard-library types. For instance a nil slice can be appended to, and a nil mutex is unlocked:

  ```go
  var things []any
  // this is fine, no panic
  things = append(things, "hi")
  ```

  But how well does this work for application data-types? What's a useful zero `BankAccountClient`? Does it just return an error on all sends (is that more useful than failing loudly, e.g. panicking?), or does it block and perform service discovery? If you pass it a zero `CloseAccountRequest` I hope it doesn't close whatever account maps to the zero value of `AccountID`. How could you make your `Server` zero value useful? Recursively that'd generally mean we'd need a useful zero value for networking clients, database clients, and useful zero values for all configuration.

  Attempting to design and rely on useful zero values for application types sounds more like an experiment in emergent behaviour than good design. I imagine calling `server.Listen` and then awaiting the random requests firing off as the various useful zero-values interact.

  But I don't think the Go authors meant this advice to be applied to applications, I think it applies only to library code foremost, and the type of data-structures we see more in systems programming (concurrency). Applications generally want to encapsulate data-structure initialization to fight complexity (e.g. always mandate constructors), so generally you don't want to worry about having zero types of your application types, and at least you know you've hit a bug if you find one.
